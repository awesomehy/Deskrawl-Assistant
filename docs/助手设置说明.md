# 助手设置

主界面右上角的「设置」打开独立弹窗。点击「保存设置」后持久保存；取消、Esc 或关闭弹窗不保存草稿。保存过程中暂时禁止关闭弹窗，避免回执落到另一次打开的设置里。弹窗正文可滚动，保存按钮固定可见。

## Steam 社区加速

- 默认关闭。开关同时控制助手内的公开市场报价、Steam 登录窗口，以及托管的 Steam 钱包、库存、行情和卖单请求。
- 开启后，后台请求先使用 Python 可识别的现有 HTTP/HTTPS 代理；没有代理时先普通直连。只读请求发生连接故障才回退到 Steam CDN 连接。收到 HTTP 错误、限流、证书错误或错误商品时不切换路线。登录窗口内的 Steam 社区页面单独使用证书校验后的 CDN 通道。关闭时保留现有系统代理/普通直连通道，不进行 CDN 回退，登录窗口也不启用独立通道。
- 不写系统代理、Hosts、DNS、环境代理变量或信任证书，不需要部署远程服务。公开报价沿用单次、随机令牌的本机反代；托管请求通过应用内 HTTPS 连接访问 Steam，不把 Cookie 交给公开报价反代。
- 加速登录使用独立、隐私模式的 WebView2 窗口。社区页面通过原生 WebResourceRequested 接口接入应用内 HTTPS，保留原始 HTTPS 地址，校验证书链和 Steam 域名后才发送请求。登录请求和 Cookie 仅在内存中转交给 Steam，不记日志、不保存密码、不安装解密证书；请求开始后不换线重发。Cookie、跨站请求和跳转仍由浏览器管理，不向页面注入助手 JS 桥。
- 加速登录入口附加 Steam 支持的 `_cdn=akamai`，由 Steam 页面生成其官方 Akamai 静态资源地址，避免默认资源线路长时间下载不完导致表单、二维码空白。登录地址仍为 `https://steamcommunity.com`，不修改页面脚本或将凭证交给第三方站点。关闭加速时不附加此参数。
- 其他官方登录、静态资源和验证码域名通过该窗口独立的本机 CONNECT 隧道访问，仅允许所需域名的 443 端口，建立后只转发加密字节。主窗口和其他软件不受影响。登录完成后仍仅提取现有会话绑定所需的两个 Cookie，由原逻辑使用当前 Windows 用户 DPAPI 保存，再由后台核验账号与钱包；核验完成前不允许出售。
- 保留证书链与 Steam 域名验证。公开报价至少间隔 15 秒；托管保留原调度频率。403/429 至少退避 5 分钟并持久保存，开关切换不会清除退避。登录页原样显示 Steam 的限制结果，不自动重试提交。尚不解析 PAC 或 SOCKS 配置；CDN 候选地址可能失效，不能保证适用于所有网络环境。
- 卖单沿用当前工作线程最近成功的只读线路，单次发送、不切线路重试。发送前仍保存提交意图；超时、断线、异常响应均保留待核实记录，下一轮和重启后不重复提交同一资产。允许类别、强制保留名单、定价/手续费、账号校验和停止托管后的提交检查均沿用现有规则。
- 保存后下一次网络请求使用新设置，正在执行的请求允许完成。已打开的登录窗口须关闭后重新打开，才能应用新开关。仅清理失败报价结果以便重新读取，保留有效缓存和限流时间。

公开报价实现位于 `steam_acceleration.py`，离线测试使用 `tests/fixtures/steam-acceleration-market.json`。

登录和托管网络实现位于 `steam_network.py`、`steam_login_window.py`、`steam_login_transport.py`。独立窗口使用 WebView2 的 [请求处理接口](https://learn.microsoft.com/en-us/microsoft-edge/webview2/how-to/webresourcerequested)、窗口参数 [AdditionalBrowserArguments](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.winforms.corewebview2creationproperties.additionalbrowserarguments) 和原生 [GetCookiesAsync](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2cookiemanager.getcookiesasync)；无全局代理设置。

Steam 库存分页、上传前后资产匹配、在售行情、提交卖单，以及待手机确认／已挂牌卖单的分页核验均走同一会话通道。界面的待确认数量来自本助手提交记录及 Steam 回读，不包含用户在其他客户端手动创建的全部卖单。显示结果最多缓存 15 秒；读取失败或重启后隐藏旧计数。内部防重复提交记录仍保留，数量暂不可见不代表允许再次出售。

登录成功后自动保存凭证并关闭窗口，无需一直打开登录页。重开助手会先核验已保存凭证；明确过期时提示重新登录，并取消、保存 Steam 自动出售开关，游戏交易所上传继续按配置执行。重新登录不会自动重新开启出售。

## 老板键与窗口

- 默认未设置，点击快捷键框后按组合键。支持 Ctrl 或 Alt 搭配字母、数字、F1–F11，可附加 Shift；数字快捷键同时支持键盘上排与开启 Num Lock 的小键盘数字键。不支持 Win、F12、Alt+F4。
- 使用 Windows `RegisterHotKey` 注册全局快捷键，按一次隐藏到 Windows 右下角通知区域（系统托盘），再按一次恢复。普通最小化后按老板键也会隐藏到托盘。
- 录入期间临时抑制老板键动作，最多 30 秒后自动解除。开始与结束录入请求依次发送，保存前等待结束录入；后端保存成功也会立即解除录入屏蔽，避免录入请求延迟导致保存后短时间内按键无效。
- 先注册新键、再原子保存、最后释放旧键。快捷键冲突或写盘失败时，旧设置和旧键保持可用。启动时如果已保存的键被其他程序占用，弹窗显示提示，用户可换键或清除。
- 点击窗口标题栏关闭按钮会隐藏到系统托盘，保留未保存的规则草稿，不停止监控、托管或其他服务。普通最小化按钮仍将窗口留在任务栏，两者行为独立。
- 双击托盘图标、托盘右键菜单「显示助手」、老板键或再次启动助手均可恢复窗口。托盘右键菜单「退出助手」与主界面电源按钮用于真正退出，保留未保存配置确认，退出时释放快捷键和托盘图标。
- 托盘采用现有 WinForms 消息循环与应用图标，不新增后台辅助进程。托盘无法创建时显示提示并退回普通最小化，保留找回窗口的入口。
- 新图标采用深色底、金色盾形 D。SVG 用于界面；`assistant.ico` 包含 16–256 像素九种尺寸，用于原生窗口和 exe。`tools/build_app_icon.ps1` 可重新生成图标，PyInstaller 已使用该 ico。

快捷键范围参考 [Microsoft RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey)，窗口生命周期参考 [pywebview API](https://pywebview.flowrl.com/api/)。

## 配置与存档

弹窗显示并打开当前实际数据目录，不接受客户端传入其他路径。位置只读，不提供迁移功能。

支持按类别独立重置，点击后再次确认，立即执行，不需要点击「保存设置」：

三项操作的二次确认弹窗分别说明清空或恢复的范围、保留的数据，以及确认后立即生效。默认焦点为「取消」；取消或按 Esc 不发送重置请求。装备筛选页、托管页的「重置改动」也需要确认，只丢弃对应未保存的修改，不清空已保存配置。

| 类别 | 重置范围 | 保留内容 |
| --- | --- | --- |
| 装备筛选规则 | 当前配置中的所有筛选组合，以及该部分未保存的草稿 | 游戏内装备锁定状态、托管与整理设置、助手设置 |
| 托管与背包仓库 | 托管、自动整理及两者共用存放页恢复默认值，清除该部分草稿 | 装备规则及其未保存草稿、老板键、Steam 加速、历史记录 |
| 浏览器缓存 | 通过 WebView2 Profile API 清理内置窗口的磁盘资源缓存与 CacheStorage | Cookie、登录、LocalStorage、助手配置和 Steam 市场报价缓存 |

重置规则或托管配置前，先暂停监控、自动整理与托管，并等待当前任务结束。运行中的任务不会被重置操作自动停止。原配置文件先逐字节备份至规则文件旁的 `reset-backups/日期时间-随机标记/`，随后使用现有原子文件事务写入默认值；备份或写入失败时不修改内存中的配置。托管与自动整理配置一起提交，保留共用存放页的一致性。

只处理所选类别的固定文件，不接受任意路径，不删除备份、日志、游戏存档、账号配置或 Steam 登录文件。缓存清理使用当前助手窗口的 WebView2 Profile，不清理系统浏览器。

发布版继续使用既有 `%LOCALAPPDATA%\Deskrawl装备助手`；已有 `runtime-paths.json`、独立账号目录或环境变量指定位置时，沿用原来的路径解析。开发版沿用工作区配置。新设置单独保存在规则文件旁的 `assistant-settings.json`，不覆盖规则、托管或其他配置。

更改默认目录本身并不必然导致新版丢失存档；关键是新版能否稳定找到迁移后的路径。本次保留现有查找方式与位置，避免引入迁移问题。
